Decision 01 Before publishing

Are the composite metrics a count-weighted average?

Architectural Value and Product Strategy each summarize several product counts into one number. Is that number, in the Power BI model, the average of the category scores weighted by how many products fall in each category?

Evidence

  • The BRD weights table gives each count its own weight: Architectural Value — Modern 5, Obsolete 1, Heritage 2, Not Approved 3 (sum 11); Product Strategy — Invest 4, Tolerate 1, Eliminate 2, Migrate 3 (sum 10).
  • The v1.3 dashboard shows each composite as a single metric of weight 10.
  • The BRD worked example follows the dashboard: the Architecture denominator of EAI 14381 is 25 = RAW Tech 5 + Architectural Value 10 + Product Strategy 10.
  • In that example Architectural Value is 97.50 with 15 Modern and 1 Heritage, and Product Strategy is 70.00 with 2 Invest, 1 Tolerate and 1 Eliminate. A count-weighted average of the category scores — Modern and Invest 100, Heritage and Tolerate 60, Obsolete, Not approved, Eliminate and Migrate 20 — reproduces both numbers exactly.
  • EAI 10969 shows composites of 75.72 and 88.37. No small set of counts produces those, so for that application the dashboard appears to receive the composite already calculated.

Options

ACount-weighted average — what runs today. The only reading that reproduces the worked example from raw counts.
BPer-count weights as in the BRD table. Changes the Architecture pillar weights and every score with products.
CAlways take the pre-calculated composite and ignore counts. Depends on CMT and MTS always delivering it.
Why it matters

The two composites carry 20 of the 100 weight points — half of the Architecture & Maturity pillar. A wrong strategy moves most applications that have products.

What runs today

Count-weighted average, weight 10 each. When a source delivers the composite already calculated, that value wins over the counts.

What we need from you
  • The DAX measure of both composites, to record as the source of truth.
  • One more real application with its counts visible on the dashboard — it becomes a third permanent regression test.
  • From CMT and MTS: do they deliver the composite, the counts, or both?
Decision 02 Before publishing

Is the Tech Debt weight 5 or 10?

The BRD weights table says 5. The v1.3 dashboard says 10. This is the one rule in the platform that no published number can currently settle.

Evidence

  • BRD weights table: Tech Debt 5. Dashboard v1.3: 10.
  • Neither case we use as proof has Tech Debt data. EAI 14381 and EAI 10969 both exclude the metric, so both score identically with 5 or with 10 — the choice is invisible to our tests.
  • If the weight becomes 5, five weight points have to be reassigned inside Architecture & Maturity, because the pillar has to keep totalling 40.

Options

AKeep 10, the published dashboard weight — what runs today.
BChange to 5, the BRD table. You would also have to say which Architecture metric absorbs the freed 5 points.
Why it matters

Every application with Tech Debt data is affected — and that is most of the portfolio once the real source is connected.

What we need from you

Do not decide this from the documents. One dashboard capture of an application that has Tech Debt data, showing its Architecture numerator and denominator, settles it numerically in five minutes.

We turn that application into a regression test and the question closes for good.

Decision 03 Before publishing

Does “zero” mean no data?

The BRD’s cross-cutting section says “null or zero values are excluded from scoring”. Several metric tables, however, name zero explicitly as a real value. Which one wins, and where?

Evidence

  • Cross-cutting rule, BRD section ALL Sections: “Null or zero values are excluded from scoring. All resulting scores are normalized within a 20 to 100 range, and null values are not included in the normalization calculation.”
  • But specific tables score zero on purpose: Tech Debt 0 → 100; SCA None → 100; MFA No (with no users) → 100; DevSecOps 0/NULL–3 → 20.
  • Measured: the two documented cases do not change. With real data, an application reporting Kenna 0 loses the best host-risk score and its denominator drops by 8 points.

Options

AThe specific table wins over the general rule — what runs today. Zero is data where the BRD scores it, and no-data where it does not.
BExclude zero everywhere. Contradicts the Tech Debt table, where 0 is the best possible value.
CNever exclude zero. An unscanned host reporting Kenna 0 would get the best risk score.
Why it matters

It changes the score of every application that reports a zero. The sharp case is Kenna: is a 0 “no risk found”, or “never scanned”?

What runs today

Zero means no data for Kenna, Open-Source Score, RAW Tech Score and Operational Score; everywhere else it scores as the table says.

When a zero is excluded this way, the calculation screen says so in words — nobody has to guess why a metric disappeared.

What we need from you

Written confirmation, plus what a Kenna 0 and an Open-Source Score 0 mean in the source systems.

If Power BI scores them, we flip one flag and publish a rules version — no code, no deployment.

Changes numbers, does not block

Each of these has a defensible default running. They are worth settling, but no date depends on them.

Decision 04 Changes numbers

When does an override replace a calculated score?

The dashboard shows two values per pillar in some cases, under an “Override rule”. When does it apply, who can apply it, is it per pillar or global, and does it expire?

Evidence

  • The platform already carries an override in its model — value, reason, who applied it, when — and the effective score uses it.
  • No source delivers overrides and no screen creates them, so the feature is inert today.
  • Until the rule exists, the platform cannot reproduce any dashboard value that was produced by an override.
What we would build

The same pattern the rules editor already uses: its own role, a mandatory reason, an audit entry, and a recent authentication required to apply it. The calculated score stays visible beside the override — an override should never hide the arithmetic.

What we need from you

The rule in one paragraph. This is one of the two items that needs code.

Decision 05 Changes numbers Application security

SCA flaws: presence or count, and who was never scanned?

Is “has at least one open critical flaw” the right reading rather than “how many”? And is there a list of applications that have actually been scanned?

Evidence

  • The BRD maps severity to a score — High/Critical → 20, Medium → 20, Low → 60, None → 100 — not a count.
  • The source has one row per flaw, so an application with no open flaws and an application never scanned look identical: both are absent.
What runs today

Presence per severity. An application that appears in the file at all — even with only closed flaws — counts as scanned. One that never appears is treated as no data, and the metric is excluded rather than rewarded with a perfect score.

What we need from you

Confirmation that presence is the right reading, and the scanned-applications list if it exists — then the heuristic becomes a fact.

Decision 06 Changes numbers

Are the band edges contiguous?

As written in the BRD, some values fall between two bands and belong to neither.

Evidence

  • Operational Score bands are 0–59.9, 60–79.99 and 80–100: a value of 59.95 belongs to no band.
  • Tech Debt bands are 0, 0.1–2.4 and 2.5–5: 2.45 belongs to no band.
  • Real Tech Debt values arrive in steps of 0.25 and never land in a gap. Operational Score could.
What runs today

The engine refuses to guess: that one application fails with an explicit error, leaves the aggregates, and shows the problem on its own screen. It never silently picks a neighbouring band.

What we need from you

The DAX conditions of those two metrics — almost certainly < 60 and >= 60. We then publish a rules version with contiguous bands.

Decision 07 Changes numbers

Is the Containerized “2 + 2 points” text still alive?

The BRD’s Containerized section says “this score is added to product strategy (2 pts) and architecture value (2 pts)”, while the weights table shows Containerized with weight 4 struck through.

Evidence

  • With Containerized, the BRD’s Architecture table sums to 40: RAW 5 + API 5 + Containerized 4 + Architectural Value 11 + Product Strategy 10 + Tech Debt 5.
  • The dashboard reaches the same 40 with a different split — RAW 5, API 5, Architectural Value 10, Product Strategy 10, Tech Debt 10 — and the worked example confirms the dashboard’s split.
What runs today

Containerized has weight 0: it is shown but not scored, and “No” does not score at all.

What we need from you

Confirmation that the sentence is superseded — and a BRD correction, so the next reader does not implement it. If a containerized application really should get a bonus inside the two composites, tell us and we model it.

Decision 08 Changes numbers

Is a LOB score the average of its applications?

When the portfolio shows a score for a LOB, a country or a CIO, is that the average of the application scores — or is it computed from the raw values added up across the group?

Evidence

  • The dashboard shows aggregates such as Suma de Kenna_Score, which suggests some measures are aggregated before scoring.
  • The two approaches give different numbers for the same group, so this cannot be left implicit.
What runs today

The average of application scores. It is explainable — click a group and you see exactly which applications produce it — and consistent with the per-application breakdown.

What we need from you

Confirmation. This is the second item that needs code if the answer differs.

Three data points we would like — not decisions

The platform already answers the six portfolio questions with the sources it has: how healthy the portfolio is, what to modernize first, where to reduce complexity, where technology risk is concentrated, what drives obsolescence and where resilience is missing. These three would turn two of those answers from indicative into real.

A · biggest effect Cost or effort per application

“What to modernize first” ranks by value per week. The only effort in today’s data is the duration of each roadmap, defined per roadmap, not per application: two applications on the same roadmap show the same weeks. It is a proxy, and the screen says so.

A t-shirt size — S / M / L — would already do.

B An “application class” column

The complexity question was asked as “more than X applications with the same application class per country”. No source carries that column, so we group by the primary business capability from the EAI master — the closest thing that exists.

One column per application, if the attribute already lives somewhere.

C Business value

Business importance is weighted today with three attributes we do have: the critical indicator, the user count and the number of capabilities covered. Revenue supported or transactions per month would replace that proxy with the real thing.

Any measure the business considers fair — even a tier.
